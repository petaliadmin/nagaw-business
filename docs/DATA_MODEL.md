# Modèle de données

> **État** : les tables `user_profiles`, `organizations`, `organization_memberships` et `audit_logs` sont **implémentées** (migration `20261020194209_tenancy_foundation.sql`, Phase 2), ainsi que `organization_invitations` et les seuils d'invitation de `organizations` (migration `20261023191420_members_invitations.sql`, Phase 4), puis `agents`, `agent_versions` et les plafonds d'agents (migration `20261023193645_agents.sql`, Phase 5), puis `responsibilities` et ses plafonds (migration `20261023210320_responsibilities.sql`, Phase 6) et son responsable (migration `20261023211917_responsibility_assignee.sql`), puis `tasks`, `task_notes` et le plafond `max_open_tasks` (migration `20261023214116_tasks.sql`, Phase 7). Les tables `agents` et `agent_versions` (Phase 5) existent encore mais ne sont plus utilisées (ADR-017) ; `responsibilities`, `tasks` et `task_notes` sont conservées mais **inutilisées** depuis le retrait de ces modules en Phase 8 (ADR-019) ; leurs plafonds (`max_responsibilities`, `responsibility_max_runs_per_day`, `max_open_tasks`) restent dans `organizations`, sans effet. Les tables `tax_rates`, `product_categories`, `suppliers`, `products`, `product_photos` et `stock_movements` sont **implémentées** (migration `20261024150000_catalog_stock.sql`, Phase 9, ADR-023), ainsi que `customers`, `sales`, `sale_lines`, `sale_payments` et `customer_payments` (migration `20261024190000_sales.sql`, Phase 10, ADR-024), puis `devices` et les colonnes d'appareil des ventes (migration `20261024210000_offline_devices.sql`, Phase 11, ADR-025) ; les autres tables boutique (§ Tables boutique) restent **proposées**.

## Conventions

- Les tables métier vivent dans le schéma privé **`app`**, que l'API Data de Supabase n'expose pas. Seul le rôle `nagaw_api` y accède, avec des droits minimaux (ADR-013).

- Clés primaires `uuid` (`gen_random_uuid()`).
- `created_at` / `updated_at` de type `timestamptz`, stockés en UTC et convertis dans le fuseau de l'organisation à l'affichage.
- Toute table métier possède `organization_id uuid not null references organizations(id)`, avec un index composite commençant par `organization_id`.
- Les statuts sont des types `enum` Postgres ou des `text` + `CHECK`. Ils sont dupliqués dans `packages/shared` pour le typage.
- Pas de `ON DELETE CASCADE` sur les historiques (`audit_logs`, `task_events`, `approval_events`) : on archive plutôt que supprimer.
- L'idempotence repose sur des contraintes `UNIQUE (organization_id, idempotency_key)`.
- Les montants sont stockés en `bigint` (unités mineures) avec un code devise ISO 4217.

## Tables boutique (ADR-019, ADR-020, ADR-023)

Conventions supplémentaires :

- les montants sont en `bigint` dans l'unité mineure de la devise de la boutique (`XOF` : pas de décimales) ; les quantités en `numeric(14,3)`, pour les produits vendus au poids ou au volume ;
- toute ligne créée depuis un appareil porte `client_operation_id uuid` avec `UNIQUE (organization_id, client_operation_id)` : c'est la clé d'idempotence de la synchronisation (ADR-020) ;
- les tables d'historique (`stock_movements`, `sales`, `payments`, `journal_lines`, factures émises) sont en ajout seul ; une correction est une nouvelle ligne (retour, avoir, contre-passation) ;
- les données modifiables partagées entre appareils (`products`, `customers`) portent `version integer` pour détecter les conflits ;
- les seuils (alerte de stock, remise maximale par rôle, durée hors ligne maximale) sont des colonnes en base, jamais du code.
